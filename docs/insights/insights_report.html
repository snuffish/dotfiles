How You Use Antigravity

You interact with Antigravity not through casual conversation, but as a disciplined execution engine driven by high-leverage slash commands and skills. You enforce strict scope definition: when a problem is open-ended or ambiguous, you systematically run /create-prompt rather than letting the agent guess. Once a plan or diagnostic proposal is created, you trigger execution with /proceed and give the agent substantial autonomy to run deep shell commands and inspect file ranges.

You make extensive use of background execution via manage_task, allowing the assistant to run build suites, test runs, and multi-file validations without blocking your interaction. You step in primarily at key architectural boundaries: reminding the agent about existing PR work, enforcing worktree isolation, or insisting that commits be staged into logical, atomic chunks rather than a single dump.

Key pattern: Prompt-first discipline (/create-prompt) paired with autonomous background task execution, where human input serves as an architectural steering wheel rather than turn-by-turn micromanagement.

Where Things Go Wrong

Most friction stems from exploratory tool thrashing when navigating code, state desync with sibling PRs, and the agent defaulting to monolithic commits.

Speculative Filesystem & Shell Search Thrashing
Agents frequently fall back to wide git grep or speculative find / commands looking for symbols or files across unindexed paths, burning tool invocations on non-zero exit codes.
  • Running broad find / -name "*PRIIS*" or sweeping node_modules directories for CSS styles.
  • Multiple consecutive failed greps in frontend subdirectories before finding the correct component path.
State Desync with Active Remote PRs
Agents frequently start diagnostic flows from scratch without checking whether a sibling PR or remote branch has already solved part of the defect.
  • Re-diagnosing a flaky test suite when the fix had already landed in Azure DevOps PR !18898.
  • User had to explicitly intervene: "1: Is already fixed... One fix is already resolved at PR !18898".
Monolithic Staging vs. Chunked Commits
When told to commit, agents default to a single git commit containing all edits rather than grouping them into logical, reviewable units.
  • User had to re-prompt: "/commit this in stages/chunks and not in one single commit."
